# Linux Basics for Hackers
## Модуль 11 — Система журналювання

---

## Про що цей модуль

Linux майже все записує — входи в систему, невдалий вхід, апаратні події, активність сервісів, помилки. Ці журнальні файли корисні з двох абсолютно різних причин, залежно від того, з якої сторони клавіатури ти дивишся. Як захисник, вони кажуть тобі, чи хтось шпигує. Як атакуючий, це запис усього, що ти зробив, і його треба прибрати, перш ніж йти.

---

## Де живуть журнали

Майже всі журнали зберігаються в `/var/log`. Перейди туди і подивися вміст:

```bash
ls /var/log
```

Ти побачиш багато файлів. Важливі, які варто знати:

| Файл журналу | Що записує |
|---|---|
| `/var/log/auth.log` | Спроби входу, використання sudo, SSH-з'єднання |
| `/var/log/syslog` | Загальні системні повідомлення — універсальний журнал більшості подій |
| `/var/log/kern.log` | Повідомлення ядра, апаратні події, помилки драйверів |
| `/var/log/messages` | Подібно до syslog, використовується в деяких дистрибутивах замість нього |
| `/var/log/mail.log` | Активність поштового сервера |
| `/var/log/apache2/` | Журнали доступу та помилок веб-сервера (якщо Apache запущений) |
| `/var/log/mysql/` | Активність бази даних (якщо MySQL запущений) |

Один з найважливіших — `auth.log`. Там є кожна спроба входу — успішна або ні — разом із IP-адресою джерела, якщо вона прийшла через мережу.

## Читання журналів

Журнали — це звичайні текстові файли. Читати їх можна будь-яким текстовим інструментом.

**Подивитися останні 10 рядків:**

```bash
tail /var/log/auth.log
```

**Слідкувати за журналом в реальному часі** (дивитися, як нові записи з'являються):

```bash
tail -f /var/log/auth.log
```

Прапор `-f` означає "follow". Це корисно, коли ти хочеш відстежити щось конкретне — наприклад, невдалі спроби входу, поки хтось активно пробує вломитися.

**Пошук у журналі конкретної інформації:**

```bash
grep "Failed" /var/log/auth.log
```

Це витягне лише рядки, що містять слово "Failed" — тобто лише невдалі спроби входу, без шуму інших подій.

```bash
grep "Failed" /var/log/auth.log | grep "192.168.1.50"
```

Тепер ти фільтруєш лог тільки за невдалими входами з конкретного IP. Так можна перевірити, чи один комп'ютер масово б'є по твоєму серверу паролями.

## `rsyslog` — той, хто реально пише журнали

Фоновий сервіс, який збирає та записує дані журналу, називається **rsyslog**. Він працює тихо весь час, слухає повідомлення від ядра та інших програм і записує їх у відповідні файли в `/var/log`.

Можна перевірити, чи він працює:

```bash
# 🐧 Debian/Kali
service rsyslog status
```

І зупинити його:

```bash
# 🐧 Debian/Kali
service rsyslog stop
```

> **⚡ CachyOS (Arch):** команди `service` там просто не існує — CachyOS повністю на systemd, і навіть класичний rsyslog там зазвичай не встановлюється окремо, бо його роль повністю виконує **journald** (компонент systemd), про який детально нижче. Якщо все ж встановити `rsyslog` (`pacman -S rsyslog`) для сумісності зі старими скриптами:
> ```bash
> systemctl status rsyslog
> sudo systemctl stop rsyslog
> ```

Якщо зупинити rsyslog, система припиняє записувати нові записи в журнал. Все, що станеться після цього, не буде зафіксовано. Це тактика, але груба — будь-який компетентний адміністратор помітить, що логування заглохло. Пропуски в журналах самі по собі є ознакою чогось дивного.

---

## `logrotate` — не дає журналам заповнити диск

Журнали ніколи не зупиняються в рості. Якщо ними ніхто не керуватиме, `/var/log` незабаром заповнить весь диск. `logrotate` — інструмент, який робить це автоматично.

Він працює за графіком (зазвичай щодня) і виконує таке:
- перейменовує поточний лог-файл (наприклад, `auth.log` стає `auth.log.1`)
- створює новий порожній `auth.log` для нових записів
- стискає старі ротаційні файли (`auth.log.2.gz` тощо)
- видаляє логи, що старші за задану кількість днів

Конфігурація, яка керує всім цим, знаходиться тут:

```
/etc/logrotate.conf          ← основний конфіг
/etc/logrotate.d/            ← конфіги для конкретних сервісів (apache, mysql тощо)
```

Відкривши `/etc/logrotate.conf`, ти побачиш параметри, як-от скільки старих версій журналів зберігати і як часто відбувається ротація. Це і є відповідь на практичне завдання в нотатках, де треба знайти, де налаштована ротація.

## `shred` — належне знищення файлів

Коли ти звичайно видаляєш файл через `rm`, дані фактично не зникають. Файлова система просто позначає цей простір як вільний. Доки щось інше його не перезапише, оригінальні дані ще фізично лежать на диску і їх можна відновити за допомогою форензичних інструментів.

`shred` перезаписує файл кілька разів випадковими даними перед видаленням, роблячи відновлення практично неможливим.

```bash
shred -vzu filename.txt
```

Розбір прапорців:
- `-v` — verbose, показує прогрес
- `-z` — після знищення додає фінальний перезапис нулями, щоб приховати сам факт знищення
- `-u` — видаляє файл після знищення

За замовчуванням `shred` перезаписує файл 3 рази. Можна збільшити кількість:

```bash
shred -n 10 -vzu filename.txt
```

Це перезаписує 10 разів перед нулями і видаленням.

**На лог-файлі:**

```bash
shred -vzu /var/log/auth.log
```

Після цього навіть якщо хтось відновить файл, він отримає випадкові дані. Лог зникне.

---

## Розумніший підхід — правити логи, а не видаляти їх

Видалення цілого лог-файлу занадто очевидно. Якщо `auth.log` раптом зник, це одразу викликає підозру — майже так само, як повна тиша в логах.

Що досвідчені нападники роблять замість цього: відкривають лог-файл, знаходять рядки, що містять їхню активність (свій IP, своє ім'я користувача, часову мітку сеансу), видаляють лише ці рядки й зберігають файл. Лог все ще існує, все ще містить дані, все ще виглядає нормально — просто з маленькою, майже непомітною діркою там, де ти був.

Щоб знайти свої записи:

```bash
grep "192.168.1.100" /var/log/auth.log
```

Потім відкрий файл у текстовому редакторі, наприклад `nano` або `vi`, знайди ці рядки, видали їх і збережи. Лог залишається цілим і не викликає підозр — просто з маленькою, майже непомітною діркою.

Це більше клопоту, ніж `shred`, але набагато менше шансів, що помітять.

## Маскування слідів — повна картина

З погляду атакуючого, чекліст очищення журналів зазвичай такий:

1. Перевірити, які логи записали твою активність — `auth.log` для входів, сервісні логи, якщо ти працював із веб-сервером або базою даних
2. Вирішити, чи редагувати (точково, менш підозріло) або знищувати (повністю, але більш помітно)
3. Очистити історію bash для сеансу — `export HISTSIZE=0` і `history -c`
4. Перевірити, чи інші інструменти не залишили слідів (IDS, логи веб-сервера, логи SQL)

Журнали розкидані по системі. Пропуск одного — це нормально. Саме тому слідчі перевіряють не лише `/var/log/auth.log`, а й інші місця.

---

## З позиції захисту

Якщо ти захищаєш систему, а не атакуєш її:

- `tail -f /var/log/auth.log` — це те, що варто мати відкритим, якщо є підозра, що хтось намагається зайти
- Повторювані записи "Failed password" з одного і того самого IP — це brute force-атака; заблокуй цей IP через `iptables` або `ufw`
- Журнал, який повністю порожній, відсутній або нещодавно "знищений" — сам по собі є доказом підробки
- Інструменти на кшталт `fail2ban` можуть автоматично блокувати IP, які надто багато разів помиляються при вході — це варто налаштовувати на будь-якій машині, що доступна з інтернету

## Довідка по командам

| Дія | 🐧 Debian/Kali | ⚡ CachyOS (journald, універсально) |
|---|---|---|
| Побачити всі лог-файли | `ls /var/log` | `ls /var/log` + `journalctl` |
| Останні 10 рядків журналу | `tail /var/log/auth.log` | `journalctl -n 10` |
| Слідкувати в реальному часі | `tail -f /var/log/auth.log` | `journalctl -f` |
| Шукати конкретний рядок | `grep "term" /var/log/file` | `journalctl -g "term"` |
| Перевірити сервіс журналювання | `service rsyslog status` | `systemctl status systemd-journald` |
| Зупинити сервіс журналювання | `service rsyslog stop` | `sudo systemctl stop systemd-journald` (не рекомендується) |
| Перезаписати і видалити файл | `shred -vzu filename` | `shred -vzu filename` (однаково) |
| Очистити історію команд bash | `history -c` | `history -c` (однаково) |
| Подивитися конфіг ротації | `cat /etc/logrotate.conf` | `cat /etc/logrotate.conf` (якщо встановлено) або `journalctl --vacuum-time=7d` |

## Практика

- Перейдіть до `/var/log` і виконайте `ls`, щоб побачити, що там є
- Виконайте `tail /var/log/auth.log` (або `journalctl -u sshd -n 10` на системах з journald) і подивіться на кілька останніх записів — там має бути ваш останній вхід
- Запустіть `tail -f /var/log/auth.log` (або `journalctl -f`) в одному терміналі, а в іншому спробуйте `ssh localhost` — побачите, як запис з'являється в реальному часі
- Створіть тимчасовий файл `echo "sensitive data" > test.txt`, потім виконайте `shred -vzu test.txt` і спробуйте знайти дані після цього
- Відкрийте `/etc/logrotate.conf` і знайдіть рядок, який регулює, скільки старих версій журналів зберігати; якщо система на journald — виконайте `journalctl --disk-usage` і подивіться, скільки місця займає журнал

## 🔄 Сучасний погляд (нотатки з практики системного адміністрування)

Модель "текстові файли в `/var/log` + rsyslog + logrotate" — це те, як логування працювало десятиліттями, і вона все ще жива на Debian/Kali за замовчуванням. Але з приходом systemd (зараз стандарт майже скрізь, включно з Debian і CachyOS) з'явився **journald** — бінарний, структурований, індексований журнал, який змінює саму модель роботи з логами, а не просто переносить ті самі дані в інше місце.

**Чому journald — це не просто "інший формат", а якісний стрибок:**

1. **Структуровані записи, а не текстові рядки.** Кожен запис journald — це набір ключ-значення полів (`_PID`, `_UID`, `_SYSTEMD_UNIT`, `MESSAGE`, `PRIORITY` і десятки інших), а не рядок тексту, який треба парсити регулярками. Це дозволяє точні запити без crazy grep-конструкцій:
   ```bash
   journalctl -u nginx.service --since "1 hour ago"     # логи тільки одного сервісу за період
   journalctl _UID=1000                                  # все, що робив конкретний користувач
   journalctl -p err                                     # тільки помилки і критичні події
   journalctl --since "2024-01-01" --until "2024-01-02"   # точний часовий діапазон
   ```

2. **Гарантована цілісність (forward secure sealing).** journald вміє криптографічно підписувати записи (`Seal=yes` в `/etc/systemd/journald.conf`, разом з `journalctl --verify`), щоб виявити факт постфактум-редагування журналу. Це прямо стосується теми "приховування слідів" вище в модулі — журнал, побудований на журналюванні з печатками, значно важче непомітно підправити рядок за рядком, ніж звичайний текстовий `auth.log`.

3. **Автоматична ротація і обмеження розміру без окремого `logrotate`.** journald сам стежить за обсягом (`SystemMaxUse=`, `RuntimeMaxUse=` у `journald.conf`) і сам ротує бінарні файли `.journal`, тому окремий `logrotate` для системних логів часто взагалі не потрібен (хоча він все ще використовується для логів застосунків, які самі пишуть у звичайні файли, наприклад веб-сервери).

4. **Персистентність — вибір, а не даність.** За замовчуванням на багатьох системах journald зберігає логи тільки в `/run/log/journal` (в оперативній пам'яті — зникають після перезавантаження). Щоб зробити журнал постійним на диску:
   ```bash
   sudo mkdir -p /var/log/journal
   sudo systemd-tempfiles --create --prefix /var/log/journal
   sudo systemctl restart systemd-journald
   ```

**Практичний висновок:** rsyslog + logrotate + grep — це те, що варто знати як базу (і це те, що досі скрізь зустрічається в production Debian-серверах), але робочий інструмент системного адміністратора сьогодні — це `journalctl`. У 90% реальних задач діагностики ("що сталося з сервісом за останню годину", "хто заходив під root учора") `journalctl -u <service> --since ...` швидший і точніший, ніж комбінація `grep`+`tail`+ручний парсинг timestamp-ів у текстовому файлі.
