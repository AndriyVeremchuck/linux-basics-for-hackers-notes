# Linux Basics for Hackers
## Модуль 16 — Автоматизація та заплановані задачі

---

## Про що цей модуль

Набирати одні й ті самі команди щодня — марна трата часу. У Linux є вбудована система планування jobs, яка називається cron; вона дозволяє сказати системі, щоб вона запускала будь-який скрипт або команду в будь-який час за будь-яким графіком. Цей модуль пояснює, як це налаштовувати, як запускати речі при завантаженні, і як працює вся система автоматизації.

---

## Cron — планувальник Linux

Cron — це фоновий сервіс, який прокидається кожну хвилину, перевіряє, чи є заплановані задачі до виконання, і запускає їх. Він був частиною Unix-систем десятиліттями і досі стандартний спосіб автоматизувати задачі на Linux.

Кожен користувач має свій cron-розклад, який називається **crontab** (cron table). У root свій. У тебе свій. Вони окремі і виконуються з правами того користувача, кому належать.

---

## Синтаксис crontab

Кожен рядок у crontab представляє одну заплановану задачу і має такий формат:

```
MIN  HOUR  DAY  MONTH  WEEKDAY  command
```

П'ять полів часу, потім команда для запуску. Поля:

| Поле | Діапазон | Що означає |
|---|---|---|
| MIN | 0–59 | Хвилина години |
| HOUR | 0–23 | Година дня (24-годинний формат) |
| DAY | 1–31 | День місяця |
| MONTH | 1–12 | Місяць року |
| WEEKDAY | 0–7 | День тижня (0 і 7 обидва означають неділю) |

`*` у будь-якому полі означає "кожен" — кожну хвилину, кожну годину, кожен день і т.д.

Декілька прикладів:

```bash
# Кожну хвилину, кожну годину, кожен день
* * * * *  /path/to/script.sh

# Щодня о 3:00
0 3 * * *  /path/to/script.sh

# Кожну середу о 3:00
0 3 * * 3  /path/to/script.sh

# 15-е число кожного місяця о полудні
0 12 15 * *  /path/to/script.sh

# Кожен понеділок-п'ятниця о 8:00
0 8 * * 1-5  /path/to/script.sh

# Кожну годину на початку години
0 * * * *  /path/to/script.sh
```

Як читати їх: заповнюй зліва направо. `0 3 * * 3` — о хвилині 0, годині 3, будь-якого дня місяця, будь-якого місяця, але лише в день тижня 3 (середа).

## Редагування свого crontab

```bash
crontab -e
```

Це відкриває твій особистий crontab у текстовому редакторі. Додавай по одній задачі в рядок. Збережи і закрий — cron зчитує зміни відразу.

**Подивитися поточний crontab:**

```bash
crontab -l
```

**Видалити всі cron-задачі:**

```bash
crontab -r
```

Будь обережний з `-r` — підтвердження немає і відміни немає.

**Редагувати root crontab** (потрібен sudo):

```bash
sudo crontab -e
```

Задачі в root crontab виконуються з повними правами root.

## Скорочення — спеціальний синтаксис cron

Замість п'ятиполівої форми cron підтримує деякі скорочення:

| Скорочення | Еквівалентно | Коли запускається |
|---|---|---|
| `@reboot` | — | Один раз при завантаженні системи |
| `@hourly` | `0 * * * *` | Кожну годину |
| `@daily` | `0 0 * * *` | Щодня о півночі |
| `@weekly` | `0 0 * * 0` | Кожну неділю о півночі |
| `@monthly` | `0 0 1 * *` | Першого числа кожного місяця |

`@reboot` особливо корисний — він запускає команду один раз після кожного завантаження системи незалежно від часу.

```bash
@reboot  /home/kali/scripts/startup.sh
```

## Практичний приклад

Напиши скрипт, який записує поточну дату й час у файл:

```bash
#!/bin/bash
echo "System check: $(date)" >> /home/kali/check.log
```

Збережи як `check.sh`, зроби його виконуваним:

```bash
chmod 755 /home/kali/check.sh
```

Заплануй його запуск кожну хвилину для перевірки:

```bash
crontab -e
```

Додай:
```
* * * * *  /home/kali/check.sh
```

Збережи, почекай пару хвилин, потім перевір:

```bash
cat /home/kali/check.log
```

Ти маєш побачити нові рядки. Коли переконаєшся, зміни графік на той, який тобі справді треба.

## Вивід cron та журналювання

За замовчуванням cron надсилає вам електронною поштою вивід будь-якої задачі, яка його видає. На локальній системі без налаштованої пошти цей вивід часто просто йде в нікуди. Щоб перенаправити його самостійно:

```bash
* * * * *  /home/kali/check.sh >> /home/kali/cron.log 2>&1
```

`>> /home/kali/cron.log` додає stdout до файлу журналу.
`2>&1` перенаправляє stderr в те саме місце, щоб помилки теж потрапили в лог.

Якщо хочеш, щоб задача працювала тихо без виводу зовсім:

```bash
* * * * *  /home/kali/check.sh > /dev/null 2>&1
```

`/dev/null` — це спеціальний файл, який просто відкидає все, що в нього записали.

## Запуск сервісів при завантаженні

Для сервісів замість скриптів стандартний сучасний спосіб — `systemctl enable`:

```bash
# 🐧 Debian/Kali
systemctl enable mysql
systemctl enable apache2
systemctl enable ssh
```

> **⚡ CachyOS (Arch):** та сама команда, але з тими самими розбіжностями в назвах юнітів, що й у модулі про сервіси:
> ```bash
> systemctl enable mariadb
> systemctl enable httpd
> systemctl enable sshd
> ```

Це створює необхідні symlinks, щоб `systemd` (система керування сервісами) автоматично запускав ці сервіси під час завантаження.

Подивитися, що увімкнено зараз:

```bash
systemctl list-unit-files --type=service | grep enabled
```

**Старий метод — `update-rc.d`:**

На старих Debian/Ubuntu-системах інколи використовується `update-rc.d`:

```bash
# 🐧 Debian/Kali (тільки)
update-rc.d mysql defaults
```

Це реєструє сервіс в старій системі init.d. `systemctl enable` робить те саме на сучасних системах і це той спосіб, який треба використовувати далі.

> **⚡ CachyOS (Arch):** `update-rc.d` там **не існує в принципі**, і це не питання іншої назви команди. Arch Linux ніколи не використовував SysV init/`init.d`-скрипти як основний механізм запуску сервісів — з моменту, коли Arch перейшов на systemd (ще у 2012 році), єдиним шляхом керування автозапуском там є `systemctl enable`/`systemctl disable`. Немає "старого способу" як запасного варіанту — тільки systemd-юніти.

## Каталоги `/etc/cron`

Поряд з crontab користувачів у системі є свої директорії:

```
/etc/cron.hourly/     скрипти тут запускаються щогодини
/etc/cron.daily/      скрипти тут запускаються щодня
/etc/cron.weekly/     скрипти тут запускаються щотижня
/etc/cron.monthly/    скрипти тут запускаються щомісяця
```

Поклади виконуваний скрипт в будь-яку з цих директорій, і він буде запускатися за цим графіком автоматично — без crontab entry. Так працюють системні задачі і ротація логів.

## Довідка по командам

| Команда | Що робить |
|---|---|
| `crontab -e` | Редагувати ваш особистий cron-розклад |
| `crontab -l` | Подивитися поточні cron-задачі |
| `crontab -r` | Видалити всі cron-задачі |
| `sudo crontab -e` | Редагувати root cron-розклад |
| `systemctl enable [service]` | Запускати сервіс автоматично при завантаженні |
| `systemctl disable [service]` | Прибрати сервіс з автозапуску |
| `systemctl list-unit-files --type=service` | Подивитися всі сервіси та їх статус при старті |

## Практика

- Відкрий свій crontab через `crontab -e` і додай задачу, яка раз на хвилину записує поточну дату у файл — перевір, що це працює через дві хвилини, потім видали задачу
- Заплануй скрипт на `@reboot` і переконайся, що він виконується після перезавантаження
- Виконай `crontab -l` для root і дивись, чи є вже заплановані системні задачі
- Увімкни MySQL для автозапуску через `systemctl enable mysql`, потім перезавантажся і перевір, чи він запущений через `systemctl status mysql`
- Спробуй записати синтаксис cron для: кожного дня о 6:30, лише в будні дні — спочатку сам, а потім перевір відповідь

Крон потребує кілька спроб, щоб звикнути. Написання кількох різних графіків з нуля — найшвидший спосіб це внутрішньо засвоїти.

## 🔄 Сучасний погляд (нотатки з практики системного адміністрування)

Cron — надійний і повсюдний інструмент, і його варто знати, бо він зустрічається практично на кожній Linux-системі в світі. Але на системах, де вже є systemd (а це і Debian/Kali, і CachyOS, і практично всі сучасні дистрибутиви), існує альтернатива — **systemd timers** — яка в багатьох професійних середовищах сьогодні є кращим вибором для нових задач.

**Чому systemd timers часто кращі за cron:**

1. **Логування з коробки, через journald.** Задача cron за замовчуванням мовчить (або, в кращому разі, шле лист поштою в нікуди, як згадано вище). Задача, запущена через `.timer`, автоматично логується в journald — можна одразу подивитися `journalctl -u my-backup.service`, без ручного `>> log 2>&1`.

2. **Явні залежності та умови запуску.** Timer-юніт може декларативно вимагати, щоб мережа була вгору (`After=network-online.target`), щоб інший сервіс уже завершився, або запускатися лише якщо попередній запуск взагалі стався (`Persistent=true` — компенсує пропущені запуски, якщо машина була вимкнена, чого cron сам по собі не вміє).

3. **`OnCalendar=` — потужніший і читабельніший синтаксис за 5 полів cron.** Приклад: `OnCalendar=Mon..Fri 08:00` замість `0 8 * * 1-5` — читається природньою мовою.

4. **Точний контроль ресурсів через systemd cgroups.** Юніт-задачу можна обмежити по CPU, пам'яті, I/O — так само, як звичайний сервіс, чого з cron-задачею зробити напряму неможливо.

**Практичний приклад — заміна прикладу з `check.sh` вище на пару systemd-юнітів:**

`/etc/systemd/system/check.service`:
```ini
[Unit]
Description=System check script

[Service]
Type=oneshot
ExecStart=/home/kali/check.sh
```

`/etc/systemd/system/check.timer`:
```ini
[Unit]
Description=Run check.service every minute

[Timer]
OnCalendar=*-*-* *:*:00
Persistent=true

[Install]
WantedBy=timers.target
```

Активація (однаково на Debian/Kali і CachyOS — це чиста функція systemd, без різниці в дистрибутивах):

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now check.timer
```

Перевірка розкладу і статусу всіх активних таймерів у системі:

```bash
systemctl list-timers --all
journalctl -u check.service       # логи запусків, без ручного налаштування
```

**Практичний висновок:** для одноразового простого крон-джоба (наприклад, особистий скрипт для домашньої лабораторії) `crontab -e` все ще найшвидший шлях — менше файлів, менше церемоній. Але для production-автоматизації на серверах — резервне копіювання, ротація, планове обслуговування — systemd timers дають кращу спостережуваність (observability) і надійність, і саме тому досвідчені системні інженери сьогодні дедалі частіше обирають їх замість класичного cron там, де це виправдано складністю задачі.
